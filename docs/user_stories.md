### US-0001 — Add a repo set and define system topology
- **Actor:** Engineer
- **As a** engineer **I want** to add 1..N GitHub repos and declare which repos form one system **so that** the engine treats them as a single analyzable whole.
- **Priority:** Must · **Status:** Done
- **AC-0001** Given valid GitHub App/PAT auth, when I add a repo URL, then it is cloned read-only and listed with commit SHA. The token comes from the auth ladder (ADR-0009): `GH_TOKEN`, then `GITHUB_TOKEN`, then `gh auth token`. `gh` is found on `PATH` or, for a desktop app launched from Finder or a launcher with a minimal `PATH`, at the standard Homebrew and Linuxbrew install paths. No token means anonymous, so only public repos can be cloned.
- **AC-0002** Given a multi-repo set, when I edit `cartograph.system.toml`, then declared layer hints and channel identities are applied at ingest.
- **AC-0003** Given an unauthorized repo, when I add it, then I get a clear auth-failure with remediation and no partial clone. The remediation says whether a credential was found and refused (check its repo access) or none was found (sign in with `gh auth login` or set `GH_TOKEN`).
- **AC-0049** Given any completed ingest, when its summary is shown, then TypeScript and Terraform each report source-file, node, and edge counts including explicit zeros.
- **AC-0050** Given a non-empty graph, when I request a clear and confirm the warning, then all graph facts are removed while durable job history remains intact.
- **AC-0076** Given accumulated terminal jobs, when I clear finished jobs and confirm the warning, then done/failed/cancelled rows are removed while queued/running/resumable interrupted jobs and all graph facts remain intact (an ended investigation's interrupted row is cleared per AC-0202).
- **AC-0077** Given the production Jobs surface, when it renders, then it offers only lifecycle verbs on existing work (Cancel/Retry/Resume and Clear finished) — no job-creation control.
- **AC-0078** Given any recovery command (ingest, add-repo, add-system, or an ingest retry/resume), when it runs, then extraction executes on a blocking worker thread — the webview/main thread never blocks, the UI stays interactive, and job progress renders throughout.
- **AC-0085** Given one or more ingested targets, when the Workspace renders, then it states what the current system contains — each repo with its commit identity, derived from the graph's own facts (never from history logs, which survive a clear) — and that further ingests merge into the same system; the destructive action is labeled in system terms (Clear system) and its confirmation names exactly what is removed (every recovered fact) and what survives (job history and settings).
- **AC-0094** Given a running recovery job (ingest, add-repo, or add-system), when I navigate away from the Recovering screen or run it in background, then it stays reachable from the status bar ("Ingesting…") and from a "View live" action on its row in the Jobs surface; while it runs, both surfaces show a best-effort, non-persisted live detail of the file and layer (application/infra/language) currently being read, throttled so it never floods the event bridge.
- **AC-0195** Given an extraction in which a node id or a (source, destination, label) relation occurs more than once — one relation cited from several call or import sites, or distinct declarations sharing one id — when it is ingested (direct, add-repo, or add-system), then the graph keeps exactly one fact per node id and per relation, the summary's node and edge totals are the distinct facts the whole operation published — the union across every repo it loaded (Repo nodes included) and every later whole-graph stage (observed BACKS stitching, found-ADR relinking), less any fact those stages retracted — so a first ingest into an empty graph quotes the same totals as the Workspace graph counts, each per-layer row counts distinct facts, and the collapsed occurrences, including a globally keyed fact published by more than one repo, are reported explicitly as merged nodes, merged edges, and node identity collisions (one id carrying differing facts) — never silently.
- **AC-0196** Given an ingest summary, when the IngestCard renders it, then merged occurrences and node identity collisions are stated beside the totals whenever either is non-zero, and no merge line appears when both are zero.
- **AC-0197** Given a local preflight, when it scans a repository, then the scan runs on a blocking worker thread rather than the invoking webview/main thread, and the Preflight surface shows live, throttled progress naming the file being read and its position in the walk — and, while the tree is still being listed, the directory being entered and how many files have been found so far.
- **AC-0198** Given a running preflight, when I cancel it (or start another preflight, which supersedes it, or switch the source away from a local tree, or change the local path, which abandons it), then it stops before reading the next file (or, while the tree is still being listed, before entering the next directory), persists no findings (AC-0215), reports that it was cancelled rather than a raw error (an abandoned scan reports nothing), and a superseded or abandoned result never replaces the current one.
- **AC-0215** Given a preflight whose register write is already in progress, when it is cancelled, superseded or abandoned, then exactly one of the two wins, decided atomically at the last step before the write commits and without Cancel ever waiting on the write: if the cancel lands first, the write is rolled back inside its transaction, the register keeps the rows it held before the write, and the scan reports that it was cancelled; if the write has already claimed its commit, the cancel loses, the findings are committed, and the scan completes and reports its result, never a cancellation (an explicit Cancel then shows that result; a superseded or abandoned scan's result is still ignored by run id).
- **AC-0202** Given an investigation ended by owner death, whose Job row is `interrupted` and offers no Retry/Resume, when I clear finished jobs and confirm, then that row is removed — the confirmation counts it — while its task keeps its interrupted or outcome-unknown status and journal in investigation history; the row is never relabelled done or failed, and resumable interrupted jobs are kept.
- **AC-0203** Given an extraction that cites one (source, destination, label) relation from several sites, when it is ingested, then the stored edge keeps the props, tier and confidence of the last occurrence in deterministic extraction order and cites the evidence spans of every occurrence with that same tier, confidence and extractor — sorted, de-duplicated and bounded, with any spans beyond the bound counted on the edge rather than dropped silently — and whenever more than one occurrence is unioned its content hash is derived from their distinct fact hashes together with the canonical span list (spans beyond the bound and their count included), so adding, removing or moving any cited site changes the hash, a single-site relation keeps its extracted hash; a collapsed relation publishes without a primary-source receipt binding, since no single receipt attested it; and re-ingesting the same commit yields an identical edge and graph hash.
- **AC-0224** Given the Connect step, when it opens with a target kept from an earlier visit, then the target field is focused with its whole value selected, so typing replaces rather than appends to it; pressing Enter in the field submits the preflight exactly when the Preflight button is enabled (never for a blank target or without a backend); and when the preflight then ends without a report (an error such as a missing path, or a cancel), the Preflight step says it did not complete and demotes Run full recovery from the primary action — it stays available, since recovery scans the target itself and fails closed if it cannot read it.
- **Security:** Tokens stored in OS keychain; never logged; least-privilege App scopes.
- **Performance:** Shallow/sparse clone; 1 GB repo clones within bounded progress feedback.

### US-0002 — Deterministic extraction of server-side facts (TS/JS/Python/Go/Java/Kotlin)
- **Actor:** Engine
- **As a** engineer **I want** import/call graphs, endpoints, and data access extracted statically **so that** server facts are Confirmed without inference.
- **Priority:** Must · **Status:** In-Progress
- **AC-0004** Given a TS repo, when ingested, then endpoints (method/path/handler) are extracted via the framework adapter and marked Confirmed.
- **AC-0005** Given typed TS, when building call edges, then intra-procedural edges are complete and inter-procedural edges resolve where types permit.
- **AC-0006** Given any extracted fact, when inspected, then it carries provenance (file/span/commit, tier, extractor_id).
- **AC-0053** Given Python that import-proves FastAPI or Flask, when the repo is ingested, then Confirmed T0 File/Symbol/IMPORTS/CALLS facts plus literal Endpoint/HANDLES registrations are recovered with exact evidence, directory-proven imported calls are joined deterministically, lookalike framework calls are ignored, and the ingest summary reports Python separately.
- **AC-0054** Given Go that import-proves `net/http`, chi, or gin, when the repo is ingested, then Confirmed T0 File/Symbol/IMPORTS/CALLS facts plus literal Endpoint registrations are recovered with exact evidence, local-package calls and handlers are joined deterministically, unresolved handler expressions retain the Endpoint with an explicit HANDLES Gap, dynamic routes and lookalike registrations are ignored, files requiring an undeclared build target are excluded, application layer hints are honored (server, events or client; since AC-0434 Go also carries client calls), and the ingest summary reports Go separately.
- **AC-0079** Given a Java repository, when it is ingested, then classes/interfaces/enums/records and methods become Confirmed T0 Symbols with exact evidence spans, same-class and import-proven cross-file calls are joined deterministically repo-wide, a declared-package import whose target cannot be proven fails closed to an explicit Gap, calls on foreign-package imports assert nothing (the import itself closes over a proven external boundary, AC-0207), and the ingest summary reports Java separately.
- **AC-0080** Given Java that import-proves Spring Web annotations (named or wildcard `org.springframework.*` imports), when a `@RestController`/`@Controller` class is parsed, then `@{Get,Post,Put,Delete,Patch}Mapping` methods become Confirmed Endpoints with class-level `@RequestMapping` path composition and HANDLES edges to their handler methods; lookalike annotations without the proving import produce no endpoints.
- **AC-0095** Given a `.js`/`.jsx`/`.mjs`/`.cjs` repo, when ingested, then the same TypeScript-crate grammar recovers Confirmed T0 File/Symbol/IMPORTS/CALLS facts and Express/Next/React-Router endpoints and screens as it does for `.ts`/`.tsx` (no separate JS adapter, and Preflight/Settings report JavaScript as installed rather than a requestable planned adapter); an extensionless relative import resolves to the real file and symbol regardless of its actual source extension once the whole directory is known, rather than a phantom `.ts`-guessed placeholder.
- **AC-0098** Given a Kotlin repository (`.kt`/`.kts`), when it is ingested, then classes, interfaces, objects, data classes, enums, and functions (top-level, member, and extension) become Confirmed T0 Symbols with exact evidence spans; same-scope and import-proven cross-file calls (type/object receivers and imported top-level functions) are joined deterministically repo-wide, with a declared-package import whose target cannot be proven — or is declared ambiguously more than once — failing closed to an explicit Gap; an import of an extension function (overloads included), top-level property, type alias, annotation class (including the grammar's expression-shaped parse of an annotated one) or enum entry resolves to its declaring File when exactly one file declares it; a call constructing an imported class or data class that exactly one file declares, and that declares no `invoke`, is a constructor call, which (as for a same-file class) is not modeled and raises no Gap, while an ambiguous class, an object's or interface's `invoke` call (wherever the operator is declared), a class declaring `invoke`, or a member the source never declares (a generated `X.serializer()`), still gaps, and a same-named factory function still resolves; calls on foreign packages and unproven receivers asserting nothing (a foreign import itself closes over a proven external boundary, AC-0207); import-proven Spring Web annotations compose class-level `@RequestMapping` with `@{Get,Post,Put,Delete,Patch}Mapping` into Confirmed Endpoint/HANDLES facts (lookalikes without the proving import produce no endpoints, and a present-but-non-literal path — on the method or the class base — fails closed to an explicit route Gap instead of a Confirmed endpoint); Preflight/Settings report Kotlin as installed (`t0.adapter-kotlin`) rather than a requestable planned adapter; and the ingest summary reports Kotlin separately.
- **AC-0099** Given a TS/JS source with an `eval()` or `new Function()` whose code argument is compile-time-known — a string literal, a substitution-free template, or a same-file `const`/const-object member proven by binding (never a name coincidence; for `new Function` the last string argument is the body and earlier ones are parameter names), then the string content is parsed by the same extractor and its Symbols, CALLS, and event sites are emitted as Confirmed T0 facts carrying `via: "eval"` with evidence citing the argument's span at the eval site, the enclosing symbol gains a CALLS edge into the extracted code's entry symbol so flows cross the eval boundary, and recovery reconciles Preflight's `inline-eval` findings from that same extraction (adapter-supplied claims, so the textual scan and the AST proof never disagree; AC-0199/AC-0200): a fully proven site's finding closes, while a const-shaped-but-unproven argument downgrades to an explicit potential Gap and any other dynamic argument — including a shadowed local `eval`/`Function` binding, which is not the global and yields no facts — stays an Unsupported finding, never a guessed fact. Every eval-recovered fact's content hash is derived from its final namespaced form (a node's label and id, an edge's label and endpoints), so the same code at two eval sites never yields distinct facts sharing one hash, and re-ingest stays deterministic.
- **AC-0100** Given how Node/TS actually resolve modules, when the directory-wide reconciliation runs, then (a) an extensionless relative import matching no file resolves through the `index.<ext>` directory convention, (b) an explicit `.js`/`.jsx` relative specifier with no such file on disk resolves to its `.ts`/`.tsx` sibling (the NodeNext idiom), (c) a bare specifier matching a tsconfig/jsconfig `paths` alias or explicit `baseUrl` resolves to the real file with the deciding config cited as provenance evidence, and (d) a bare specifier naming a workspace package inside the ingested tree resolves through that package's `exports`/`module`/`main` map with its `package.json` cited; every resolution is a proof against files that exist — unmatched specifiers keep their explicit `mod:` node or placeholder, and external packages are never resolved into. The tsconfig parse is shared with the toolchain detector's stored facts (parse once, `adapters-fw::tsconfig`).
- **AC-0192** Given a proven Spring mapping in Java, when its path is a string literal or an array initializer of string literals (`@GetMapping({ "/vets" })`, `value = { "/a", "/b" }`), then each literal becomes its own Confirmed Endpoint composed with the class base, and an empty or absent path takes Spring's default; when the path on the method or the class-level `@RequestMapping` is present but not provably literal (a constant, a concatenation, any expression), then the mapping yields an explicit route Gap bound to its handler and no Endpoint — never a fabricated `/`.
- **AC-0199** Given a local preflight, when it scans TS/JS sources, then it performs no TS extraction (no AST parse, #243) and reports every textual `eval(`/`new Function(` line as an Unsupported `inline-eval` finding marked pending AST proof at recovery — none is claimed closed or downgraded, and none is dropped.
- **AC-0200** Given a completed local recovery, when its TS extraction has classified the eval sites, then the register's preflight findings for that repo are replaced by the textual scan of the captured bytes the claims were proven on (not the live tree), reconciled with those claims (AC-0099), so the register and the Preflight surface (which receives the reconciled report, potential-Gap lane included, with the recovery's summary) quote the post-recovery classification and no pending wording survives. The reconciliation scan runs only after the recovered facts are published, and its write goes through the per-repo fence only once the recovery's job has settled as completed, so a recovery that fails earlier, or is cancelled at any point before it completes (even during the reconciliation scan), leaves the pending findings in place; a preflight of that repo that began before the reconciliation cannot overwrite it afterwards, while a preflight started after recovery is newer and reports the lines as pending again until the next recovery (attested reuse of the recovery's proof is #438).
- **AC-0201** Given a TS/JS `eval()` or `new Function()` whose code argument is const-shaped (an identifier or member expression) but not provable to a literal, when the file is extracted, then the site becomes exactly one explicit `Gap` node — `attempted_tiers: ["T0"]`, a reason stating the argument could not be proven to a literal, and Gap-tier provenance citing the call site plus every unproven argument (inside proven eval code, the one outer-literal span instead, AC-0213) — owned through `DEPENDS_ON` by its enclosing symbol (or its File at top level), with an id keyed by repo, path and site offset so the same source yields the same Gap on every run and in the captured production lane; nothing about the site is asserted as Confirmed, and proven or dynamic sites emit no such Gap; a proven `eval()` whose code itself holds such a site is claimed const-unproven rather than covered, so Preflight keeps its potential-Gap finding, and a nested Gap's content hash derives from its final namespaced id.
- **AC-0209** Given a completed GitHub-backed (`add_repo`) or system-manifest (`add_system`) recovery, when its TS extraction has classified the eval sites, then each recovered repo's register preflight findings are replaced exactly as a local recovery's are (AC-0200): the textual scan of the captured bytes, reconciled with that repo's claims (AC-0099), scanned only after the recovered facts are published and written through the per-repo fence only once the recovery has completed. The recovery summary carries the reconciled report — a single report for a GitHub add, one per repo in manifest order for a system add. A recovery that fails or is cancelled, including a system recovery whose later repo fails after an earlier one recovered, writes no repo's findings.
- **AC-0214** Given a local, GitHub-backed or system-manifest recovery, when it publishes its job as completed, then its reconciliation's place in the per-repo fence (AC-0200, AC-0209) is already reserved and every source it wrote is ready and released, so a preflight of that repo started after the job shows done can read it and is always newer than the reconciliation: if that preflight persists first, the reconciliation writes nothing over it, and if it persists afterwards it is not refused. - **AC-0216** Given preflight reports and recovery reports for the same repo that settle in any order — a preflight that overlapped a recovery, or a recovery re-run from Jobs → Retry — when they reach the Preflight surface, then the register order decides which is shown, not the order they arrive in: every register write carries its epoch; a preflight that a recovery reconciled past answers with the reconciled report the register holds instead of reporting a cancellation; a recovery's report replaces the shown report when no preflight began since the recovery started or when the shown report is the same repo's, and never when its reconciliation wrote nothing because a newer preflight's findings, or an overlapping recovery's newer reconciliation of that repo, were already there; the surface never shows an older report for a repo than the newest it has received. A retried recovery returns its reconciled report with the retried job row, applied under the same rule.

### US-0045 — Recover the journeys users take through a client
- **Actor:** Reviewer or developer
- **As a** reviewer **I want** each client's screens, the navigations between them and the server calls made on the way recovered from source **so that** I can follow what a user does to reach a goal and which server behavior each step reaches, without trusting a model's account of it.
- **Priority:** Must · **Status:** Draft
- **AC-0349** Given a `new VueRouter({ routes })` or `createRouter({ routes })` call whose callee is import-proven from `vue-router`, when the repository is ingested, then its route table is read when `routes` is an array literal, a `const` bound to one, or a call of a relatively imported function or class static method whose body returns one array literal. Each route object with a `path` becomes one Confirmed `Screen` (`screen:{repo}@{path}`, `router: "vue-router"`) citing the route and the registration. A path is a string literal or a member of a `const` object of literals, directly or through a class static field naming or holding one (`Navigation.PATH.MAIN`); a child path joins its parent's. The Screen `RENDERS` its component's file when the component is a relatively imported local, or a key of a `const` object of such imports passed as the table function's argument (`getRoutes(components)` with `components.Main`). The edge is Confirmed when the import names the file it resolves to; an extensionless import found only as an existing `.vue` file assumes the bundler's extension list, and its edge is InferredStrong with `resolution: "vue_extension_assumed"`. An import with an explicit extension names only that file or, for `.js`/`.jsx`, its NodeNext TypeScript source; it never falls back to `.vue`. A redirect without a component renders nothing; the same route registered twice is one Screen, and a rendering registration wins. A computed path, a table that does not resolve, or a component that does not resolve is a Gap (kind `route-unresolved`) naming the site, the last linked from its Screen by `RENDERS`; nothing is guessed. A local `VueRouter` not imported from `vue-router` registers nothing. The coverage matrix claims `vue-router` client routes for JavaScript and TypeScript, and partially for Vue, whose templates (and so `<router-link>` targets) are not parsed.
- **AC-0350** Given recovered Vue Router screens, when the repository is ingested, then a navigation becomes one InferredStrong `NAVIGATES_TO` edge from the Symbol whose body performs it (or the file, at module level) to the target `Screen`, with `router: "vue-router"`, `router_basis: "this.$router"` and `conditional`, citing each call. A navigation is either a direct `this.$router.push(target)` or `.replace(target)`, or a call of a relatively imported function or class static method that passes one of its parameters, unshadowed, to `router.push` or `router.replace`. In the second case, `router` must be a module `let`/`var` assigned only by setters of that file (`router = $router`), and some file must call such a setter with `this.$router`. The target is a literal, a constant-table member of the caller's file, or `Owner.FIELD.KEY` of a relatively imported class's static table. Calls from one Symbol to one Screen are one edge, since the store keeps one edge per source and target; it lists every call under `sites` in source order, each with its span, `via` (`direct` or `wrapper`) and its own `conditional`, and the edge is conditional only when every call is under an `if` branch, `switch` case, `catch`, conditional expression or the right of `&&`, `||` or `??`. A computed target, or one that names no recovered Screen, is a Gap (kind `navigation-unresolved`) linked by `NAVIGATES_TO`. Back navigations (`router.go(-1)`, `router.back()`) are not read.
- **AC-0351** Given an `entryProvider { … }` call whose callee is import-proven from `androidx.navigation3.runtime`, when the repository is ingested, then each `entry<X>(…) { … }` call in its trailing lambda with one type argument `X` that resolves to a uniquely declared repository type becomes one Confirmed `Screen` (`screen:{repo}@navigation3:{fqn}`, `router: "navigation3"`, `key: fqn`) citing the entry, or a `route-unresolved` Gap when `X` is not a declared repository type. Each top-level call statement in the entry's trailing lambda whose callee resolves to a repository function Symbol emits a Confirmed `RENDERS` edge from the Screen to that Symbol; callback arguments passed into entries emit no edges, and a local `entryProvider` registers nothing. In a class with a back-stack property initialized to `mutableStateListOf<NavKey>(…)`, `MutableStateFlow(mutableStateListOf<NavKey>(…))` or `rememberNavBackStack(…)` (with `NavKey` and `rememberNavBackStack` import-proven from `androidx.navigation3.runtime` and `MutableStateFlow` from `kotlinx.coroutines.flow`), each `add` on that property (`p.add`, `p.value.add`, or `add` inside `p.apply` / `p.value.apply`) — directly, through a same-class `NavKey` parameter helper that adds its unmutated parameter, or through a same-class `(…) -> NavKey` builder helper that adds the result of calling its parameter directly or via a local `val` — emits one InferredStrong `NAVIGATES_TO` edge from the enclosing function Symbol (or the enclosing class Symbol in an `init` block or property initializer) to the target `Screen`, with `router: "navigation3"`, `router_basis: "back_stack"`, `conditional` and `sites` (`via`: `direct`, `param_helper` or `builder_helper`), or a `navigation-unresolved` Gap when the target is computed or names a declared type with no recovered Screen. A back-stack initializer's single key argument marks its recovered `Screen` with `initial: true` and `back_stack_owner`, citing each initializer in the Screen's provenance (plus sorted `initial_owners` when named across classes), navigation sites in `init` blocks or property initializers carry `phase: "init"`, and callback arguments (`::fn`, non-overloaded `recv::fn`, or a single-call lambda; an unqualified name inside `with(recv) { … }` resolves to `recv`'s member first) passed to a rendered composable are recorded on the `Screen` under `entry_callbacks` with `read` (false only when the composable never references the parameter) and up to four direct parameter-forwarding hops. `removeAt`, `removeIf` and `clear` are ignored. The coverage matrix claims `navigation3` client routes partially for Kotlin.
- **AC-0352** Given recovered path-router `Screen` nodes with entry screens (`route == "/"`), `RENDERS` edges to component files or symbols, `NAVIGATES_TO` edges between screens, stitched `FETCHES` edges to server `Endpoint` nodes, and traced server flows, when the spec bundle is compiled, then rule `journey-candidate@1` recovers bounded T2 `InferredWeak` journey candidates (`ProducingMethod::Rule { rule: "journey-candidate", version: "1" }`) and renders them in `journeys.md`. Each screen's rendered-code call closure walks `RENDERS` targets (`Symbol` directly, or `Symbol` nodes with `DEFINED_IN` to a rendered `File`) and same-repo `CALLS` edges up to `max_calls_per_screen = 64`. Simple paths from each entry screen up to `max_screens = 6`, `max_expanded_states = 256` and `max_candidates = 32` per entry stop at the first step whose closure calls a goal `Endpoint`: a server flow reaching a `WRITES` edge to a `DataEntity` (`goal_basis: "observed_write"`) wins over an HTTP `POST`/`PUT`/`PATCH`/`DELETE` call with no observed write (`goal_basis: "method_assumed"`, `write_coverage: "unknown"`), and earlier assumed-write calls before an observed write are listed under `earlier_assumed_goals`. A post-goal `NAVIGATES_TO` from the same `Symbol` and file path whose unconditional site starts at or after the fetch's `byte_end` appends one ordered result step (`result: "ordered"`); a navigation before the call, in another function, or only at a conditional site leaves `result: "unordered"`. Cycles are not re-entered, shortest paths win per `(entry, goal)` with extra simple paths counted in `alternatives` (`alternatives_complete: false` when any budget bound truncates), and unresolved `FETCHES` or `NAVIGATES_TO` `Gap` edges on a step are preserved without stopping traversal. Candidate `id` hashes `(version, budget, step_screen_ids, navigations_taken, goal.endpoint)` while `support_fingerprint` hashes the supporting steps, goal, flows, static test references and truncation state. Initial destinations (`initial: true`) are also entry screens; startup (`phase: "init"` on the back-stack owner) and read `entry_callbacks` navigations are crossed only as recorded `startup` / `entry_callback` assumptions with their limitation (every read registration reaching a crossed callback is listed and its registration span cited) while unread callbacks are listed on the step, and `journeys.md` shows a per-entry search summary. In `verified-only` export, T2 `InferredWeak` journey candidates are excluded and `journeys.md` states why; in `best-effort` export, each candidate renders with inline provenance and states that it is a static path candidate and not a recorded session or runtime trace.
- **AC-0353** Given a Kotlin call `x.m(…)`, `x?.m(…)` or `this.x.m(…)`, when the repository is ingested, then it resolves to a T0 `Confirmed` `CALLS` edge to `T.m` (`resolution: "declared-type"`, evidence the call span) when the nearest lexical binding of `x` states its type `T`: a function or lambda parameter, a primary-constructor `val`/`var` property or class-body property of the enclosing class (or of an outer class from an `inner` class), a plain constructor parameter outside member functions, or a local or top-level property with a type annotation or a `T(…)` initializer. Nullable and generic forms (`T?`, `T<X>`) denote `T`. `T` names, in Kotlin's precedence, an explicit import, a same-file type through the enclosing type chain, the same package, or a star-imported package; the first FQN this repository declares exactly once decides. A nearer binding with no stated type (an inferred or delegated local, a loop variable, a destructuring entry, an implicit `it`) blocks outer bindings. A member `T` does not declare, a duplicate FQN, or a `T(…)` initializer whose `T` is not a constructible class (or is also a top-level function) asserts nothing and produces no `Gap`.
- **AC-0354** Given a Kotlin `hiltViewModel` call whose callee is import-proven from `androidx.hilt.navigation.compose` or `androidx.hilt.lifecycle.viewmodel.compose`, when the repository is ingested, then a binding initialized by it has a declared type for AC-0353: `hiltViewModel<VM>(…)` denotes `VM`, and `hiltViewModel(…) { f: F -> f.m(…) }`, whose last expression calls a method on its single typed parameter, denotes the declared return type of `F.m` (resolved in `F.m`'s own file, as for a view model `@AssistedFactory`). Inside `with(x) { m() }`, where `x` is such a call or a binding with a declared type, an unqualified `m()` resolves to `T.m` before the enclosing class and file; when `T` does not declare `m`, the call keeps its ordinary resolution. A same-named function that is not import-proven, a callback of any other shape, and a `with` receiver with no declared type type nothing.
- **AC-0355** Given a Kotlin `@Binds` function in an abstract class or interface that carries import-proven `@dagger.Module` and `@dagger.hilt.InstallIn(SingletonComponent::class)` in a main source set, whose only other annotation is `@Singleton` and whose single parameter type `Impl` and return type `Iface` are plain repository types without type arguments, where `Impl` is a concrete class that directly declares `Iface` as a supertype and no other such binding names `Iface`, when the repository is ingested, then each member `m` declared on both gets an `InferredStrong` `CALLS` edge `Iface.m -> Impl.m` (`resolution: "hilt-binds"`, `assumption: "hilt_dispatch"`, `binding` the bind function, evidence the `@Binds` declaration), and the declared-interface edge stays `Confirmed`; any other component, qualifier, multibinding, generic key, duplicate key or non-main source set yields no edge. A journey candidate crosses such an edge only as a `hilt_dispatch` assumption naming the interface member, the implementation and the binding, inherited by everything it reaches; proven calls dominate, and the journeys artifact shows the row as `Iface.m → Impl.m`.
- **AC-0356** Given a journey candidate whose goal endpoint is fetched inside an anchor's flow (a Screen, extension context or command), so the endpoint has no flow of its own, when its goal basis is decided, then the writes observed for that endpoint are those of the Symbols the flow reaches downstream of the endpoint (its handler and their callees). A write upstream of the endpoint (a client-side Symbol) is never the endpoint's, and the candidate's flow and test listings are unchanged.
- **AC-0357** Given Python code using a session proven as SQLAlchemy's (a module-level `scoped_session(…)` or `sessionmaker(…)()` with the factory import-proven from `sqlalchemy.orm`, or `<db>.session` of a proven Flask-SQLAlchemy instance), when the repository is ingested, then `S.add(M(…))`, `S.add(x)` or `S.delete(x)` with `x = M(…)` earlier in the same body, `S.add_all([M(…), …])` and a `S.query(M)….delete()` / `.update(…)` chain give a `Confirmed` `WRITES` edge from the enclosing function to `M`'s `DataEntity` (`resolution: "session"`, `operation`, sorted `operations`, evidence the confirming call). A call `X.m(…)` on a recovered model class gives an `InferredStrong` `WRITES` edge (`resolution: "model-helper"`, `via: "<Class>.m"`) when `m`, resolved on `X` then its repository bases depth-first, is a `@classmethod` that writes its own `cls` that way. An override that does not write, an unresolvable base before the definition, a helper writing another model, a local or unimported `Session`, a non-model class, `getattr`, an instance call and a write in another function give no edge.
